# 日志说明

日志有两类：**系统日志**（一行一条事件，排查用）和 **Agent 轨迹**（一次思考一个 JSON 文件，看"它为什么这么建议"用）。

## 一、系统日志 `logs/app.log`

- 标准库 logging，**控制台和文件双输出**（前台跑 uvicorn 时终端里看到的就是它）。
- 按天滚动（午夜切割，保留 14 天，旧文件名形如 `app.log.2026-08-06`）。
- 格式：`真实时间 [级别] 消息`。注意**行首时间是真实时间**，消息里业务涉及的"今天"才是虚拟时钟。

实时跟看：

```bash
tail -f logs/app.log
```

### 会记哪些事件、怎么解读

| 日志样例 | 含义 |
|---|---|
| `api POST /api/offwork status=200 耗时=9.1s` | 每次 API 请求：方法、路径、状态码、耗时（静态页不记） |
| `user=demo1 event=offwork 触发建议生成` | 用户点了「下班了」且开始跑 Agent |
| `llm_call model=qwen-plus tools=['search_reference'] 耗时=2.1s` | 一次模型调用：这轮模型决定调哪些工具；`tools=无(最终输出)` 表示这轮直接给结论 |
| `user=demo1 agent round=2 tool=search_reference args={...}` | Agent 第几轮、调了什么工具、什么参数 |
| `user=demo1 json解析失败，重试第1次` | 模型输出不是合法 JSON，自动重试中（WARN） |
| `user=demo1 agent round=1 模型调用失败，走兜底` | 模型挂了，返回写死的默认建议（ERROR，演示不死） |
| `user=demo1 vision识别失败，走兜底` | 食物照片识别失败，按"一餐饭"记录 |
| `clock 虚拟时钟变更 -> 2026-08-13T19:00:00` | 演示控制条/接口改了虚拟时间 |
| `user=demo1 event=feedback record=12 vday=... 反馈=完成了` | 回执写库 |
| `user=demo1 回执修改导致档位 3→2，重出今晚建议` | 用户改回执触发的连锁重算 |
| `event=correct type=今晚更累` / `event=free_input text=...` / `event=meal_photo 识别=咖喱饭` / `event=meal_delete` / `event=profile_update` | 各类用户动作 |
| `db 迁移：profiles 表补充 wake_time 列` | 启动时的轻量迁移 |

### 常用排查命令

```bash
grep 'ERROR\|WARN' logs/app.log            # 只看异常
grep 'event=' logs/app.log | tail -20      # 最近的用户动作流水
grep 'user=demo1' logs/app.log             # 只看某个用户
grep '兜底' logs/app.log                    # 是否触发过降级
```

**"演示时为什么建议不对"的排查顺序**：先 `grep user=xxx` 看当时那几行 → 确认调了哪些工具、有没有走兜底 → 再去看对应的 trace 文件（见下）核对注入的上下文。

## 二、Agent 轨迹 `logs/trace/`

每跑一次 Agent 主循环（下班了 / 一击纠正 / 自由输入重出 / 改回执重出 / 首夜建议）生成**一个缩进格式的 JSON 文件**：

```
logs/trace/2026-08-13_demo_m7_190523.json
           └─虚拟日期──┘└─用户名┘└─虚拟时分秒┘
```

### 文件结构

```jsonc
{
  "user": "demo_m7",
  "virtual_time": "2026-08-13 19:05 （周四）",
  "context": "【用户档案】…【当前虚拟时间】…【今天已知】…【最近3天】…【当前最低线档位】…",
      // ← 这就是那次注入给模型的完整上下文。建议不对时先看这里：模型"知道"什么
  "rounds": [
    {"round": 1, "tool": "search_reference", "args": {"query": "...", "category": "sleep"},
     "result_brief": "检索结果前200字"},
    {"round": 1, "tool": "log_note", "args": {"text": "今晚加班3小时…"}, "result_brief": "..."},
    {"round": 2, "output": "{...最终 JSON...}"}      // 没有 tool 字段的是模型直接输出
  ],
  "final": { "judgement": "...", "move": null, "sources": [...] },   // 最终建议
  "duration_s": 8.9                                                  // 本次总耗时（秒）
}
```

### 怎么用

- 前端建议卡片下的折叠面板「它是怎么得出这个建议的」就是读的最新一份 trace（`GET /api/agent_trace`）。
- 核对"数字是不是工具算的"：看 rounds 里有没有 `calc_body_metrics`，比对 `result_brief` 里的数值和 final 里引用的数值。
- 核对"为什么没提到中午吃的"：看 `context` 的【今天已知】里有没有那条饮食记录。
- 文件按名字排序即按时间排序，看某用户最新一次：`ls logs/trace/*_demo1_*.json | tail -1`。

## 三、uvicorn 自身的日志

uvicorn 的访问行（`INFO: 127.0.0.1:xxx - "GET /api/state" 200 OK`）只打到控制台，不进 `app.log`。排查以 `app.log` 为准即可。
