## 一、B3：/api/correct 新增「换一种做法」

- `CORRECT_TYPES` 加项（白名单校验，旧项不动）。
- 处理为**一次性条件**（参照难度微调）：不写入 `conditions["纠正"]`——写入会让"换个做法"永久跟着每次重生成、方向漂移；档位不变、不查封顶。
- 注入行由纯函数 `_switch_plan_line` 拼接：`用户希望换一种做法：目标和量级保持不变，给出与上一版不同的具体做法（上一版：吃=…；动=…）`，eat/move 为 null 时对应段省略、双 null 时整个括号段省略。
- rejected 用户走既有 severe_flag 拒绝分支（接口顶部守卫，先于类型分支）；重生成结果照常全量过 enforce。

**实测**（真实服务连点两次）：三版 eat 完全不同（清蒸鱼套餐 → 白灼虾仁套餐 → 虾仁蒸蛋羹套餐）、move 具体动作轮换（肩颈拉伸 → 猫牛式 → 抱膝滚动）而量级不变（都是 5+5 分钟）；落库 `档位=3`、`纠正列表=[]` ✅。

## 二、B4：GET /api/history

- `db.get_history_records`：只取 `vday/advice_json` 两列——**feedback 从源头就不出库**；`advice_json IS NOT NULL`、倒序、SQL LIMIT 30。
- `_history_items`（纯函数）再做一层防御：输出键固定 `{vday, line, items}`，`line` 取 `advice.stop` 缺则 `judgement`，`items` 为 eat/move/stop 非空行；二次截断 30。
- **硬规则落实**：响应绝不含 feedback、绝不含连续天数统计（PRD 原则五：不做成绩单）。severe_flag 用户返回 `{rejected:true, message}` 与其他接口口径一致。

**实测**：demo1 返回 3 条、键集合正确、全文无 "feedback"/"连续" ✅；新空号返回 `{"history": []}` ✅。

## 六、问题与潜在问题

1. **B3「换一种做法」的 move 变化幅度看模型心情**：实测三版 move 前半段（靠墙静蹲）有重复、后半段轮换。注入行只给了上一版摘要，没有硬性"逐项必须不同"的校验——模型偶尔可能换汤不换药。属体验项非安全项；若后续想收紧，可在注入行里点名"eat 和 move 都要换"。
2. **B3 连点无次数限制**：每点一次都重跑模型（一次性条件不累积，不会漂移，但也没有到顶提示）。P4 前端注意别做成可疯狂连点的按钮（复用现有防双击即可）。
3. **B4 line 用 stop 原文**：advice.stop 偶尔带说明性长句（如"22:30 放下手机，准备入睡"），s-history 窄屏可能折行。前端可截断显示，接口不再加摘要逻辑（避免引入改写）。
4. **B4 上限 30 条不分页**：按计划一次性返回，长期账号（>30 天）只见最近 30 天。够演示用；真要翻页是后续需求。
5. **B5 旧前端仍提交旧名**：P3 重建前 onboarding.html 还在发 粉面类/甜品奶茶/家常菜，靠归一化兜住（已实测）。P3 上线后 data-val 换新名，归一化保留不删（老库存量值永远可能在）。
6. 沿用已知未修：A1 同步 LLM 阻塞（本次三步 curl 串行无感）。
