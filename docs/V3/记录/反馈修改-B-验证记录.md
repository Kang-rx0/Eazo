## 一、落地清单

### 3. onboarding 问「今天经历了什么」并真实参与决策（纯前端，零后端改动）

**界面**（`s-ob-2`，照 v0.2 原型补回，两组都带 `data-todayonly`）：
- chips「今天有没有额外动一动」：`没有，就这样`（默认选中）/ `运动了一下`；
- 一行自由输入「今天还有什么特别的」，placeholder「可不填。比如：中午吃了火锅 / 下午淋了雨」。

**不进 profile**：`exercise_today` 与 `todayNote` 都不在 `buildPayload()` 里，`/api/onboarding` 收不到它们；编辑态（`?edit=1`）两组整体隐藏（对齐 v0.2 `data-todayonly` 语义：这是今天的事，不是长期底子）。

**参与决策的机制**（`sendTodayOnly()`）：首次走完 onboarding、`/api/onboarding` 返回 200 之后，把**非默认答案**拼成一句话 POST `/api/free_input`，然后才跳 `app.html`。
- 拼法：选了「运动了一下」→ `今天已经运动过一次`；输入框有内容 → 原文；两者都有用 `；` 连接。
- **全默认且没填 → 空串 → 不发请求**。
- 发送失败不拦路（档案已经存好，不该把人堵在 onboarding）。
- 后端零改动：`/api/free_input` 当天无建议时只存库并回「记下了。晚上生成建议时会考虑进去。」；当晚生成时 `db.get_free_inputs(user_id, vday)` 同时喂给**【今天已知】的"用户自由输入"**和 **`safety.assess` 三层安全检测**。

## 三、问题与潜在问题

1. **cooking 旧值不迁移是有代价的**：库里 demo1 仍是 `只能外卖`，注入提示词的也是这句原文（`平时吃饭：只能外卖`），只有用户进一次编辑态并保存才会变成新值。也就是说**同一时期库里会新旧值混存**，看提示词时别以为是 bug。计划明确"demo 账号数据不迁移，靠映射兜住"，照做。
2. **`主要吃食堂` 是新增语义**，旧三选里食堂是并进"只能外卖"的（原注释：「食堂」并入只能外卖）。现在食堂单独成一档，模型看到的条件变了——回归 18/18 说明没有破坏安全边界，但建议内容的口味可能和以前不完全一样。
3. **今天那一句只在"首次走完 onboarding"发一次**。用户如果在 onboarding 里填了"下午淋了雨"，然后当晚很久之后才点「开始今晚」，这句话仍然有效（按 vday 存，当天有效）；但**跨过午夜就失效**，属于设计内。
4. **发送失败是静默的**（`catch` 里什么都不做）。设计意图是不拦路，代价是极端情况下（断网）用户填的那句话丢了却没有提示。若要更稳，可以在 app.html 首页 toast 一句"刚才那句已记下"，本批未做。
5. **两个 today-only 问题都不带"跳过"语义**：chips 有默认值、输入框可空，等价于可跳过，所以没有额外的跳过链接。与 onboarding 其余步骤的「跳过」样式不同，是有意为之。
6. **`exercise_today` 用了 `data-one` 组名但不进 payload**。将来若有人给 `buildPayload` 加"把所有 data-one 组自动收进 payload"这类通用逻辑，会把它误带进 profile。已在 HTML 注释标明，改的人要注意。
