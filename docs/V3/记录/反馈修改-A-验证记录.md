## 一、落地清单

### 1. 时钟条：可加可减 + 10 分钟档（第 1 条）

- **后端** `backend/main.py` `/api/clock` 新增 `advance_minutes`，实现即 `clock.advance_hours(float(minutes)/60)`（计划原文方案，`clock.py` 未动）。三个 `advance_*` 都天然支持负数（`timedelta` 特性），docstring 与 400 错误文案同步补 `advance_minutes`。
- **前端** 时钟条按钮由 `+1小时 / 下一天 / 重置` 三个扩到七个：`−1d −1h −10m ｜ +10m +1h +1d ｜ 重置`（mono 小标签，逐字对齐计划）。
- **布局**：430px 单行放得下七个按钮，但会把时间显示挤成 `2026-08…` 省略号（实测截图为证）。按"演示道具的时间必须完整可读"处理成**折行**——时间独占第一行、七个按钮排第二行，两行都完整。样式写在 `app.html` 页内 `<style>`（`.clockbar{flex-wrap:wrap}` 等三行），`nightwatch.css` 的 token 与基础规则未动。

### 2. 全局返回（第 2 条 + Q1）

- `BACK_TO` 新增 `advice → confirm`（原有 `confirm→home`、`settings→home`、`history/about→settings` 不变）。
- **不可返回名单**维持：`accepted`、`bye`、`rejected`（`done` 是批次 D 才新增的屏）——都不在 `BACK_TO` 里，返回箭头不出现。
- 返回处理加了一道兜底：目标是 confirm 且 `renderConfirm()` 拿不到 `confirm_hint` 时退回 Home，不会停在空白 confirm 屏。
- **Q1 落地**：新增 `applyConfirmLock()`，`show('confirm')` 时执行——`currentAdvice` 存在则三处「改一下」`hidden+disabled`，`voice` 行换成提示行「今晚已生成，要改走「我要补充」。」。不做后端强制重算。
- ob-1 返回键按 Q9 默认**维持隐藏**（`onboarding.html` 本批未改动）。

### 3. 下班询问首问时刻 +5 分钟（第 7.1 条）

- `checkReminder` 里 `end.setHours(h, m, 0, 0)` → `setHours(h, m + 5, 0, 0)`（JS 自动进位，跨小时/跨天安全）。其余逻辑（答「还没」30 分钟后再问、最多两次、答过或自主开始即不再问）一行未动。

### 4. 演示起点改下午 4 点（用户体验后追加，当面拍板"三处都改"）

`backend/clock.py` 加常量 `DEMO_START = datetime(2026, 8, 24, 16, 0)`，三个落点统一：

| 落点 | 旧 | 新 |
|---|---|---|
| 当前虚拟时刻 | 2026-08-24 19:10 | **2026-08-24 16:00** |
| `advance_days(±1)` 换天后的时刻 | 19:00 | **16:00** |
| 「重置」按钮 | 真实系统时间（2026-08-09） | **回演示起点 2026-08-24 16:00** |

「重置」原来跳真实系统时间，会离开演示数据所在的日期、把种子态打乱，演示时没有任何用处，一并收掉。
同时按拍板重跑 `scripts/seed_demo.py` 把 demo1 恢复标准种子态（08-22 已完成 / 08-23 待回执 / **08-24 空**）——此前开发测试给 08-24 生成过建议，登录会直接落在结论屏，不是交接文档写的标准演示路径。

### 5. 拨时钟不再把人弹回 Home / 结论屏（用户体验后追加）

用户原话：拨时钟是为了**跨过某个节点**（下班点、睡点、新一天），不是为了刷新页面；4:00→4:30 什么都没触发，页面不该跳。

`refreshState(opts)` 新增 `opts.keepScreen`，只有时钟条按钮传 `true`。停在当前屏，但下面三种"真的发生了事"仍然切视图：

- **跨天**（`state.vday` 变了）→ 全量切视图并作废 `currentAdvice`（这正是用户说的"反馈更新点"）；
- **劝退**（`view === 'rejected'`）→ 永远切，安全赢过一切；
- **当前屏不成立**（人在结论屏但新状态已经没有建议）→ 退回 Home。

另外停在 s-confirm 时会重跑 `renderConfirm()`，三行判断跟着新时间重算。其余调用方（生成/纠正/自由输入）不传 `keepScreen`，行为与改动前完全一致。

### 6. 结论屏时间带：未到下班点时从下班点起画（已知问题 #6，用户体验后追加）

旧算法 `路上 = 到家时刻 − 现在`，在下班前会把"还在办公室干等"的时间也算成通勤：demo1 下午 4 点看会显示 **「路上 220 分」**（实际通勤只有 40 分）。起点挪到 16:00 之后这个瑕疵天天露脸，按拍板一并修。

新算法：未到下班点（且下班点早于到家时刻）时，横条左端锚在**下班点**而不是"现在"，左端标签显示 `19:00 下班`。两段都是真实时长。到点之后行为与原来完全一致。

### 7. 编辑资料「保存失败」的两个真 bug（用户体验中报出，当场修）

用户在设置 → 基本情况改完点「存好了」报"保存失败，稍后再试一次"。复现后定位：

**直接原因（环境）**：本会话为恢复种子态重跑了 `scripts/seed_demo.py`，脚本会**删掉 demo1 再重建**，连带清空 `sessions` 表，用户浏览器里的旧 token 随之失效，所有接口返回 401。

**由此暴露的两个前端缺陷（已修，`frontend/onboarding.html`）**：

1. **onboarding 不处理 401**。`app.html` 的 `api()` 遇 401 会清 token 跳登录页，`onboarding.html` 的 `submit()` 只看 `res.ok`，登录过期一律报"保存失败"，用户只会反复重试。
   → `submit()` 增加 401 分支：清 token、跳 `auth.html`。
2. **预填失败后保存会覆盖真实档案（数据损坏，更严重）**。编辑态的三个时间滚轮靠 `prefill()` 调 `setWheel` 灌值；`prefill()` 失败时是静默 `return`，滚轮停在列表**第一项**——上班 `06:00`、下班 `16:00`、起床 `05:00`。此时点保存，用户真实作息会被这三个垃圾值覆盖。实测那次 401 的 payload 正是 `{off_work_start:"06:00", off_work_end:"16:00", wake_time:"05:00"}`，只因为接口也 401 才侥幸没写进去。
   → `prefill()` 改为返回布尔；失败时置 `prefillFailed`、**禁用「存好了」**并提示"没读到你的资料，先刷新一下再改"；`submit()` 也加同一道闸。401 在 `prefill()` 里直接跳登录页。

### 8. 前后端一致性收口：档案值域与字段语义（用户体验中提出，当场处理）

原则：**界面能表示的值域，必须覆盖库里可能存在的每一个值**——覆盖不了就会静默改数据。三处按这个原则收：

**8.1 `off_work_start` 语义对齐（后端跟前端走）**

界面 ob-1 问的是「一般几点上下班」，左轮=上班、右轮=下班，还用 `off−on` 算工作时长；而后端把它当"下班时间范围起"：

| 位置 | 旧 | 新 |
|---|---|---|
| `db.py` 建表注释 | `-- 下班时间范围起 / 止` | `-- 上班时间（ob-1 左轮，列名沿用历史）/ 下班时间（右轮…）` |
| `agent.py` `_fmt_profile` | `下班时间 09:00–19:00，偶尔加班` | `上班 09:00，下班 19:00，偶尔加班` |
| `seed_demo.py` 两处档案 | `off_work_start='18:00'` | `'09:00'`（18:00 不在上班轮 06:00–14:00 档位内） |

列名 `off_work_start` 保持不变（改列要迁移，收益不抵风险），语义以注释和提示词为准。`off_work_start` 在后端只有这一处消费点，到家/剩余时间/下班提醒全都只看 `off_work_end`，所以语义澄清不改变任何行为——**但提示词动了，全量回归必跑**。

**8.2 时间滚轮不再把越界值吸附成默认值**

`setWheel` 原来是"值不在档位表里就停在默认值"。种子里的 `off_work_start=18:00`、任何老账号的非半点时间，进编辑态都会被悄悄换掉，保存后永久生效。
→ 新增 `insertWheelOption()`：值是合法 `HH:MM` 但不在表里，就**按时间顺序插进滚轮再选中**（跨零点的下班轮按 +24h 排序）。只有值本身非法（空/格式错）才回落默认值。

连带修 `wheelMinutes()`：原来按"索引 × 30 分钟"算工作时长，插入非标准档位后索引算法会失真，改成直接解析当前值。

**8.3 通勤 chips 不再吸附到最近档位**

原来是 `nearest = [15,30,45,60] 里最近的一个`，种子的 `40` 会被改成 45。
→ 新增 `setOneOrAdd()`：没有对应 chip 就**补一个 chip 再选中**。配套把 `[data-one]/[data-many]` 的逐元素监听改成**事件委托**，否则后插进来的 chip 点不动。

## 三、问题与潜在问题

1. **回拨跨天的既有行为（计划已列，不修）**：回拨到前一天后，那天若已有建议，`/api/state` 仍会回到那天的 advice 屏——演示道具的固有行为。
2. **`advance_days(±1)` 会把时刻归到演示时刻 16:00**，不是"同一时刻加减一天"。这是 `clock.advance_days` 的原有语义（只把落点从 19:00 换成 16:00）；想要精确跨天要用 `set`。
3. **时钟条从一行变两行**，底部占高多约 20px，所有屏的可视区相应缩短一点点。430×880 下六屏实测无内容被压掉；更矮的设备（如 375×667）没有逐屏复测。
4. **advice→confirm 返回后，confirm 屏的三行判断是"当下重算"的**（`renderConfirm` 读最新 `confirm_hint`），可能与生成建议那一刻的数值不同（剩余时间随时钟走）。这是 hint 纯代码估算的必然结果，不是数据不一致；Q1 已经把「改一下」关掉，不会造成误改。
5. **Q1 采取的是"隐藏 + 禁用"**（`hidden` 同时 `disabled`），不是视觉置灰。计划写的是「置灰/隐藏」二选一，这里选了隐藏——理由是禁用态的 textlink 在暗色下和正常态几乎看不出区别，隐藏 + 一行明确提示更不容易误点。若更想要"看得见但点不动"的形态，去掉 `b.hidden = locked` 一句即可。
6. **提醒 +5 分钟只影响首问**，第二次仍是"首问后 30 分钟"（即下班点 +35 分钟）。计划第 7.1 条明确"其余逻辑不动"，此处照做。
7. **`reminderOff` / `offworkReminder` 仍是 localStorage**（既有设计），换设备不跟随；本批未改。
8. **回归脚本用例 14/15 隐式依赖虚拟时钟的位置（本批实际踩到，非产品 bug，值得留档）**：
   这两例直接用既有账号 `demo_dm2` / `demo_hbp` 调 `/api/offwork`，而这两个账号只有 `2026-08-24` 一条**未回执**记录。
   - 时钟停在 08-24：`/api/offwork` 走 `already_generated` 短路，返回那条存好的建议 → 四项内容检查全过；
   - 时钟被拨到 08-24 之后（本批做提醒验证时拨到了 08-26）：08-24 变成"昨日及更早未回执"，接口返回 `need_feedback`（**没有 `advice` 字段**），脚本里 `a = {}`，14/15 双双假失败 → 误报 16/18。
   本批第一轮回归就是这么误报的，把时钟复位到 `2026-08-24 19:10` 后重跑得到 18/18。
   **给后续会话的操作要求**：跑 `safety_regression.py` 前先确认虚拟时钟在 `2026-08-24`；批次 D 要动的正是"凌晨回初始页 / 拨时钟"这一块，验证时更容易踩到。
