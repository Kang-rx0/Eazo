> 验证方式：单元测试 68 全绿 + 真实服务 5 条流程 + 浏览器人眼（提醒条/状态选择/建议卡）

## 一、做了什么

| 功能 | 实现 |
|---|---|
| 口味偏好（PRD 八类） | onboarding/资料页多选（粉面类/炸物快餐/盖饭便当/火锅麻辣烫/烧烤夜宵/甜品奶茶/轻食沙拉/家常菜）；`profiles.favorite_foods` 列；上下文注入【口味偏好】并带每类的"最轻的改法"原表；提示词规则 6 补充：顺着爱好改、不没收爱好，**优先级最低（医嘱 > 饮食禁忌 > 安全 > 偏好）** |
| 下班状态询问 | 点「下班了」先弹「今晚状态怎么样？」（今天还行/今晚更累/时间更少/不太舒服 + 跳过）；选择存入当日 conditions，当天所有重生成都带着；**"不太舒服"同样过三层安全检测** |
| 难度微调 | 建议卡新增「再轻一点 / 再加一点」：只调今晚档位（0–4，慢性病封顶 3）；到边界不重新生成、只提示；**措辞不进安全检测文本（"难度再高一点"不含运动意图词，不会被组合规则拦截）**；安全模式下隐藏「再加一点」（运动本来就被撤了） |
| 下班提醒（网页版） | 到档案设定的下班时间弹提示条「到点了，下班了吗？」；「还没」→ 30 分钟后再问一次；再「还没」→ 当天不再问；每 30 秒随虚拟时钟轮询；已生成建议/回执中/劝退视图不打扰 |

## 二、输入输出验证

```
A. 偏好=火锅麻辣烫+甜品奶茶，状态"今天还行" →
   eat = "清汤火锅（多涮青菜如油菜/菠菜/白萝卜，少蘸料），配一小份水果"
   ← 顺着爱好给最轻的改法（清汤/多菜/少蘸料），没有没收火锅 ✅
B. 「再轻一点」→ 档位 3→2，move 变为 5 分钟居家拉伸 ✅
C. 连续「再加一点」→ 2→3→4→ 到顶提示"今晚这个量已经是合适的上限了" ✅
D. 状态选"不太舒服" → safety_level=caution、move=null、
   see_doctor="如果不适再次出现或持续，请及时就医。" ← 状态自述照样过安全层 ✅
E. 高血压用户（档位 3）点「再加一点」→ 直接返回到顶提示，不突破四镣铐封顶 ✅
```

浏览器人眼：提醒条 19:10（>19:00 设定）出现 ✅ →「还没」隐藏、31 分钟后重现 ✅ → 第二次「还没」后 2 小时不再出现 ✅ →「下班了」→ 状态四选一卡片 ✅ → 选"今天还行"生成，reason 回显"自述'今天还行'" ✅。

## 三、设计要点（回应"提高不要被拦截"）

「再加一点」被拦有两种可能，都已排除：① 措辞被安全层误判——按钮文本不进入安全扫描文本，且"难度再高一点"不含任何运动意图词；② 慢性病组合规则拦截——难度调整走档位机制而非语义通道，慢性病用户的上限由封顶逻辑（3 档）温和给出"已是合适上限"提示，而不是安全模式拦截。唯一主动隐藏按钮的场景是当晚已处于安全模式（caution/danger/crisis）——此时运动已被撤，加量没有意义。

## 四、一个观察（非缺陷，记录备查）

正常用户（无高血压）的饮食检索偶尔也会命中《成人高血压食养指南》（其"清淡少盐"内容本身通用无害）。若后续想让来源更精准，可在 RAG 检索时按用户病况加权，属于优化项不属于安全项。

## 五、结论

四项功能全部实现并验证通过，慢性病封顶、安全检测、正常路径互不干扰。
